# Core Flows

## Navigation

The app uses hash routing. `AppShell` renders stable navigation links to
`#/dashboard`, `#/records`, and `#/components`; `App` maps the current hash to dashboard,
records, record detail, or component showcase. Record detail URLs are generated by
`routes.record(id)`.

## Command And Settings Surfaces

`AppShell` opens `CommandMenu` with `Cmd/Ctrl + K` or the sidebar utility
button. The command menu can navigate to dashboard or records, or open the
settings modal. Theme changes flow through `SettingsPanel` and `useTheme`.

## Example Records

`RecordsPage` calls `ExampleRecordRepository.findAll()` on load. Seeding refreshes
the full list. Counts and filters operate on all loaded records, without a
page limit; repository pagination remains available independently.

The record list uses hover and focus to update the inspector preview. Clicking a
record link navigates to `RecordDetailPage`.

Loading, successful empty results, and read failures are separate states.
Read failures use `patterns/content-state.tsx`'s `ErrorState` with a retry action.
A failed refresh preserves the last successful records and reports that they
have not been refreshed; a successful retry clears the error.

## Record Detail

`RecordDetailPage` is keyed by record ID. Reads and mutations belong to that
mounted record instance; obsolete responses cannot update the current page. It loads one record by ID. Edit mode uses local form state and
persists through `ExampleRecordRepository.update()`. Delete uses
`ConfirmDialog`; on success it returns to the record list hash route.

A successful detail query returning `null` means the record does not exist;
a rejected query displays a retryable read error. Saving exits edit mode and
reports success only when `update()` returns a record. A `null` result or thrown
error retains the input and displays a persistent `ErrorState` near the form.
The missing-record save error provides a link back to the list. Successful save
or cancelling edit clears the save error.

## Database Connection

Concurrent native calls share the pending database load, and a successful
connection stays cached. Failed loads clear the cached promise and rethrow the
error, allowing the next user-triggered retry to load again. There is no
automatic retry or fallback from native failure to the browser mock.

## Feedback

Successful save and transient operation notifications use `FeedbackToast`;
read and save errors remain next to the affected content through `ErrorState`.
Delete failures retain the existing toast behavior. General app notifications
are wired through `Toaster`.

Record list, detail and component showcase assign each notification a unique ID.
A new operation dismisses its
previous notification by ID, and a late close callback only clears the matching
instance. Sonner owns the close lifecycle, so an exiting notification cannot
remove the next successful save notification.
